# S3 跨进程传输耗时评估

## 设备、版本与口径

下方主表的三批原始样本来自统一策略接口重构前的实现。重构后的 JSON 带有 `implementation: strategy-v1` 和每种输入的方案列表，另有一批 S3 回归记录。

2026-11-18，在一台 S3 设备（Android 11，API 30，arm64-v8a，系统构建 RKQ1.211119.001）运行 arm64 调试包。设备通过 USB 供电，屏幕点亮。用正常首页进入 Demo，本次启动关闭 Gecko 页面预热。通过不同 PID 确认客户端与服务端跨进程，两端属于同一应用 UID。

被测工作区基于 TechLab `00546631f4863c69f9e9bfb710e9645ffc2922fe`，叠加本专题实现。安装 APK 的 SHA-256 为 `a2175eb6bc6b6896abb837f982a6b1ee952a9c14c26ae7e11550a09d9fc941d5`。模块源码与配置指纹为 `70165dcc929e5b0014d83de5add1334e321237f7583f40942309a88fa50b7519`（在 Android 工程目录按路径排序，将 `demo-binder/build.gradle.kts` 与 `demo-binder/src` 下各文件的相对路径、NUL、内容、NUL 依次送入 SHA-256）。

- **已有文件**。相同的应用缓存文件已生成并顺序读过，用于计算参考 CRC32。输入包括 32 KiB、1 MiB、8 MiB 确定性二进制数据，以及一份已生成的编码文件。四条路径按轮次循环错开顺序；分块 Binder 对 8 MiB 发起 256 次同步请求，每块打开、定位并关闭源文件。
- **现场编码**。生产端的输入已在内存中准备好。实验用 PNG 编码器作为确定性字节生产者，每次从同一输入重新生成相同输出。文件路径的临时文件只写入页缓存并关闭，没有 `fsync` 持久化要求；管道路径由写线程直接把编码字节交给消费者。数据内容、编码器、读取分块与校验相同。
- **首块**从客户端发起传输计到累计收到 32 KiB；管道单次 `read` 可能更短，累加到相同门槛。**完整**计到长度与 CRC32 均通过、句柄关闭，含 IPC、复制、调度与校验。共享内存计入区域创建、映射、填充、收紧保护和解映射。连接服务、准备样例、查询元数据、样本解码与后续处理与结果写盘均在计时外。
- 每条路径每种输入每批预热 2 次，再测 20 次。连续运行三批，合并相同输入和路径的原始纳秒样本后计算最近秩 P50 和 P95。设备没有锁频或清理系统页缓存；本次仅覆盖单客户端串行传输。

### 如何选

1. **数据已在普通文件中时优先交付只读 FD。** 对预生成的 1,705,378 字节，文件 FD 完整 P50 为 2.99 ms，管道为 25.12 ms。8 MiB 文件的三批 FD 完整中位数分别为 9.46、9.38、9.34 ms。客户端直接读已打开的同一文件，服务端无需启动写线程再复制一遍。少量控制字段可与 FD 一起交付。
2. **按需生产、接收方可以顺序消费时，优先评估可靠管道。** 对相同生成过程，从请求到收到首个 32 KiB，先写文件为 320.02 ms，直接编码到管道为 31.80 ms；完整校验分别为 349.18 和 309.03 ms。三批里管道的首块与完整 P50 均更短。管道让读取与编码重叠。对必须收齐才能继续的调用者，应采用完整校验耗时。
3. **小消息保留 Binder 直传，大对象慎用逐块 RPC。** 32 KiB 单次返回的完整 P50 为 1.74 ms，与文件 FD 的 1.67 ms 接近。8 MiB 分成 256 次返回时增至 273.13 ms，约为文件 FD 的 29 倍。这个差值同时包含同步 IPC 及逐块开关文件，不能据此推断一次 Binder 调用的固定成本。
4. **共享内存适合另行评估内存原生或多读者场景。** 这里从已有文件出发，每次创建区域并填满后才能读。8 MiB 首块 P50 为 30.53 ms，完整为 56.94 ms；这组数字不覆盖预先建立、反复复用同一区域的生产方式。跨应用延迟打开已有文件可选带临时读权限的 Content URI，双向长连接可考虑本地 socket，这两种入口仅做机制比较。

## 完整性与异常回收

三批客户端 PID 为 7980，生产端 PID 为 8089。每批经文件 FD 和管道分别顺序接收 3 个不同的确定性样本，三批共 18 次。逐个核对请求标识、长度、CRC32，并对解码后的结构和标记值进行校验。两条按需编码路径的长度与校验值均等于预生成文件的参考值。所有计时样本也通过长度和 CRC32 校验。

每批 4 轮异常检查分别提前关闭文件读端、管道读端，并让另一条管道在写入 4 KiB 后失败。每批均识别 4 次显式写错，另有 4 次管道读端取消导致的写错；结束时在途写任务为 0。三批的客户端 FD 前后分别为 84→84、83→83、83→83，服务端为 55→55、56→56、56→56。这是短批次的资源回收记录。冷磁盘、跨 UID 授权、多客户端并发、长时间压力及接收后的端到端处理均留作其他工作负载。

## 统一策略接口后的 S3 回归

同日从首页进入新版 Demo，点击运行、取消，页面显示「测量已取消」。再次运行后显示「对照完成」。本批有 18 个输入与方案组合，每组 20 条有效样本。客户端 PID 为 8427，服务端 PID 为 8614。样本内容与请求标识的匹配检查通过，异常检查结束后在途写任务为 0，客户端和服务端 FD 数分别保持在 83 和 57。调试 APK 的 SHA-256 为 `2df1902bd065e8e9f9480a0aee3d0969fcea970679ac8c46a766f20ed7b99be5`。[本批原始报告](evidence/strategy-v1/s3-run-1.json)

本批 8 MiB 已有文件经只读 FD 完整读取的 P50 为 9.72 ms。按需编码时，可靠管道的首块 P50 为 27.64 ms，先写临时文件为 319.14 ms。单批结果用于复核方案行为，旧版三批数据仍用于上方选型比较。

python3 summarize.py evidence/s3-run-*.json
python3 summarize.py evidence/strategy-v1/s3-run-1.json
